# Claude sidecar

A thin TypeScript process around the Claude Agent SDK. The daemon (`qireid`) starts one per active
agent session and speaks bounded JSON Lines over stdin and stdout. See ARCHITECTURE.md, "Agent runtime (Claude)".

It owns no policy. It translates SDK messages into protocol events and relays every permission request and
question to the daemon, then waits for the answer. The Rust side validates every event and decides every
permission.

## Build and test

Node.js is pinned in `.nvmrc` (exact version, matched by `engines`); the SDK and every other package are pinned to exact versions in `package.json`.

```sh
cd sidecars/claude
npm ci --ignore-scripts
npm run build   # tsc: type-checks the real SDK calls against the installed SDK types
npm test        # node:test over dist/test
```

`npm run bindings` copies the protocol types generated by `crates/runtimes` (`crates/runtimes/bindings/*.ts`)
into `src/generated/`. Run it after changing `crates/runtimes/src/protocol.rs`; the copies are committed so the
sidecar builds without Rust.

## Protocol

- One JSON object per line, at most 1,048,576 bytes without the newline. A longer command line is discarded as it
  arrives and reported once as a `log` event; an event too large to send is dropped and logged, and a too large
  permission request or question is denied.
- `ready` is the first event and carries the protocol version and the SDK version.
- stdout carries protocol lines only. Diagnostics are `log` events; stray console output goes to stderr. No log
  carries a token, an environment value or tool output.
- `shutdown`, or the end of stdin, denies every pending request, stops every run and exits with code 0.

## Permission gate

- Every tool call, from the main session or a subagent, reaches a `PreToolUse` hook. The hook sends
  `permission_request` and returns the daemon's `answer_permission`: `allow` (optionally with a new input) or
  `deny` with its message. No code path allows without that answer.
- `canUseTool` handles `AskUserQuestion`: the questions go out as a `question` event and the
  `answer_question` labels come back as `updatedInput.answers`, joined with `, ` for multi-select. The SDK still
  sends `AskUserQuestion` to the gate first, so the daemon must allow it there.
- The SDK's own safety checks (for example writes under `.git/`) can send a call the daemon already allowed to
  `canUseTool`. Such a call is sent to the daemon again as a fresh `permission_request` with the same
  `tool_use_id` and `reason: "sdk_safety_check"` (and an `info` log `sdk safety check: ...`), and that second
  answer applies. The daemon decides it anew; it never reuses the first answer. A call with no
  recorded allow, for example after a hook error or timeout, is denied.
- SDK options: `settingSources: []`, `allowedTools: []`, `permissionMode: 'default'`,
  `includePartialMessages: false`, and the options of the start fields below. `allowed_tool_names` only narrows the SDK's built-in tool set (`tools`); an
  empty list keeps the SDK default.

## Start fields from the agent settings

The `start` command carries what the owner's agent settings switched on, taken by the daemon once when the run
starts. The sidecar checks the shape and maps the fields to SDK options. It decides nothing: every tool call of the
main session, a skill or a subagent still goes to the daemon.

| Start field | Shape | SDK option | Notes |
|---|---|---|---|
| `skills` | list of text, optional | `skills` | Each entry is `qirei-skills:<name>`. Always passed, an empty list included, so the CLI's own default skills are not offered when nothing is switched on. |
| `skills_plugin_dir` | text, optional | `plugins: [{ type: 'local', path }]` | The run's generated skills folder. Only set when at least one skill was copied; with no folder there is no `plugins` option. |
| `agents` | map name to definition, optional | `agents` | A definition is `description`, `prompt`, and optional `tools`, `disallowed_tools`, `model`, `skills`, `mcp_servers` (connector names), `max_turns` and `permission_mode` (`default`, `plan` or `dontAsk` only). They become the SDK's `tools`, `disallowedTools`, `model`, `skills`, `mcpServers`, `maxTurns` and `permissionMode`. No `agents` key when none are sent. A name such as `__proto__` is an ordinary name. |
| `mcp_servers` | map name to `{ command, args }`, optional | `mcpServers` | Local stdio programs only. A server with any other field (`env`, `url`, `type`, `headers`) refuses the whole command, so no value travels with a connector. No `mcpServers` key when none are sent. |
| (always) | | `strictMcpConfig: true` | The CLI starts only the servers named above and ignores a `.mcp.json` in the work folder, plugin servers and user settings servers. |

A field of the wrong type refuses the command (the run does not start). The option names were read from the
installed SDK's type definitions (`@anthropic-ai/claude-agent-sdk`, `sdk.d.ts`); how the real CLI treats them is
checked only by the manual smoke run (questions 4 to 6 in the guide below). The daemon also adds
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=3` and `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=20` to `start.env`; the sidecar's own
allowlist does not include them.

## Environment

The SDK child, and every tool it runs, gets only `PATH`, `HOME`, `USER`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`,
`TMPDIR`, `SHELL`, `TZ` and `NODE_ENV` from the sidecar, plus `start.env` from the daemon. The daemon passes the
Claude credential, and nothing else secret, through `start.env`. With the sandbox required (the default) that is a
placeholder credential (`ANTHROPIC_API_KEY`, or `CLAUDE_CODE_OAUTH_TOKEN` for a setup token) plus `ANTHROPIC_BASE_URL` (the daemon's loopback credential gate), `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`,
`CLAUDE_CONFIG_DIR`, `HOME` and `TMPDIR` (the run's own home and its `tmp` folder), `BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS` and four git settings
(`GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=safe.bareRepository`, `GIT_CONFIG_VALUE_0=explicit`, `GIT_CONFIG_NOSYSTEM=1`);
the real key is never here. Only with `sandbox = "off"` does the real credential travel in `start.env`. The sidecar
runs under `sandbox-exec` with a per-run policy; it merges `start.env` last, so these names win over its
allowlist. As a second line of defence the daemon must spawn
the sidecar with a cleared environment (`env_clear()` and only what the sidecar itself needs). If the daemon closes
the sidecar's stdout, the sidecar denies every pending request, stops its runs and exits 0.

## Manual smoke run

The tests never call the real SDK, the real CLI or the real API. The one manual run against them, with the questions
it must answer (whether the real CLI works against the daemon's loopback credential gate, whether the `PreToolUse`
allow is enough for ordinary tools, whether `settingSources: []` keeps user skills and plugins out while the generated skills plugin still loads, the
skill, subagent and connector name forms, plus the
safety-check re-ask, the fixed environment and the sandbox's denials), is in
[docs/superpowers/spikes/agent-smoke.md](../../docs/superpowers/spikes/agent-smoke.md). The owner runs it, in a
scratch repository only, with a throwaway or low-limit key.

Until that run is done the sidecar's behaviour inside the OS sandbox (`sandbox-exec`, see ARCHITECTURE.md, "OS
sandbox") is verified only with stand-in programs and a scripted SDK, not with the real CLI.

## Layout

| File | Role |
|------|------|
| `src/main.ts` | Entry point over process stdio |
| `src/sidecar.ts` | Command loop, runs, answer routing |
| `src/gate.ts` | `PreToolUse` gate, `canUseTool` for questions, pending requests |
| `src/map.ts` | SDK message to event mapping |
| `src/lines.ts` | Bounded line reader |
| `src/protocol.ts` | Protocol constants, command parsing, event encoding |
| `src/queue.ts` | Async queue feeding user messages to a run |
| `src/sdk.ts` | SDK adapter and the real `query()` options |
| `test/fake-sdk.ts` | Scripted SDK used only by tests |
